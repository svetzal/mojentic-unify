# oMLX gateway, September 2026

The contract every port implements for a gateway to
[oMLX](https://github.com/jundot/omlx), an LLM server for Apple Silicon. Elixir
implements it first and is the reference where this document is silent.

The capability ships in **2.1.0** in all six ports, together with the work in
`ALIGNMENT-2026-09.md`. Swift is already on 2.0.0, and the other ports skip
2.0.0 so the same version means the same features everywhere. Kotlin's first
published release is 2.1.0.

## Why a separate gateway

oMLX speaks the OpenAI chat completions protocol, so the OpenAI gateway can
reach it with a different base URL. That is not enough:

- The OpenAI model registry rewrites requests for model names it does not
  know. It removes `reasoning_effort` for unknown models, and its substring
  patterns (`o1`, `o3`, `o4`) can classify a local model as an OpenAI
  reasoning model, which removes tools and renames `max_tokens`.
- Most ports drop `reasoning_content`, so thinking traces are lost.
- OpenAI embeddings chunk input with the OpenAI tokenizer at 8191 tokens,
  which is wrong for local embedding models.
- The OpenAI environment variables collide with a real OpenAI configuration.

The oMLX gateway reuses each port's OpenAI message adapter and OpenAI stream
parser. It does not use the OpenAI model registry, and it does not adapt
parameters per model.

## Evidence

Captured on 2026-09-29 from oMLX 0.7.0rc1 serving `Qwen3.8-27B-MLX-8bit`.
The raw responses are in `fixtures/omlx/`. Use them as test fixtures. The
behaviour below is what the server did, not what its documentation says.

## 1. Configuration

| Setting | Constructor or option | Environment | Default |
| ------- | --------------------- | ----------- | ------- |
| Host | `host` | `OMLX_HOST` | `http://localhost:8000` |
| API key | `api_key` | `OMLX_API_KEY` | none |
| Timeout | the port's existing idiom | `OMLX_TIMEOUT` | the port's OpenAI default |

- The host has no `/v1` suffix. The gateway adds `/v1` to every path, the same
  way the Ollama gateway adds `/api`.
- Precedence: explicit value, then environment, then default. Ports whose
  gateways are configured only by environment (Elixir) use the environment.
- With an API key, send `Authorization: Bearer <key>`. Without one, send no
  authorization header.
- Name the gateway `OMLX` plus the suffix the port uses for its OpenAI gateway
  (for example `Mojentic.LLM.Gateways.OMLX`, `OMLXGateway`).

## 2. Chat completions

`POST /v1/chat/completions`. Build the body from the configuration with no
per-model adaptation:

| Config | Request body |
| ------ | ------------ |
| model | `model` |
| messages | `messages`, through the OpenAI message adapter |
| temperature | `temperature` |
| max_tokens | `max_tokens`. Never `max_completion_tokens` |
| top_p, top_k | `top_p`, `top_k`, when the port's config has them and they are set |
| reasoning_effort | `reasoning_effort`, unchanged, when set. Omit when null |
| response_format | as `ALIGNMENT-2026-09.md` section 1 (OpenAI-compatible) |
| tools | `tools`, as the OpenAI gateway sends them |
| num_ctx, num_predict | not sent. oMLX sets context length per model |

`reasoning_effort` goes to the model's chat template. Its effect depends on
the model. Document that. A null value leaves the model's default, and
Qwen 3 models think by default.

Structured output requests (the port's object or schema API) send
`response_format: {type: "json_schema", json_schema: {name: "response",
schema: <schema>}}`. Do not use an OpenAI SDK's strict-mode parse helpers.
Validate content against the schema as the port already does.

Response mapping:

| Response | Gateway response |
| -------- | ---------------- |
| `choices[0].message.content` | content |
| `choices[0].message.reasoning_content` | thinking |
| `choices[0].message.tool_calls` | tool calls, as the OpenAI gateway parses them |
| `choices[0].finish_reason` | finish reason |
| `model` | provider model |
| `usage` | usage, exactly as reported |

oMLX adds fields to `usage` (for example `model_load_duration`,
`time_to_first_token`, `generation_tokens_per_second`). Keep them. Never
estimate usage.

### Unenforced structured output

When oMLX cannot compile a grammar, it degrades `json_object` and
`json_schema` to instructions in the prompt, and it reports this in a
`Warning` response header. When a request asked for structured output and the
response has a `Warning` header:

- put the header value in response metadata under `response_format_warning`
- log a warning

Do not retry and do not fail. This is evidence, not policy.

### Truncation during thinking

When `max_tokens` ends generation during thinking, a non-streaming response
puts the partial reasoning in `content`, `reasoning_content` is null, and
`finish_reason` is `length` (`fixtures/omlx/chat_length.json`). A streaming
response keeps it in `reasoning_content`. Map the fields as they arrive. Do not
move text between them. Document that `content` is not an answer when the
finish reason is not `stop`.

## 3. Streaming

**Events API** (`ALIGNMENT-2026-09.md` section 3): supported. Use the port's
OpenAI-compatible stream parser and completion rules unchanged. Send
`stream_options: {include_usage: true}`. `reasoning_content` deltas produce no
events. The events API has no thinking event.

**Legacy streaming API**: behave like the port's OpenAI gateway, with these
differences:

- `delta.reasoning_content` becomes the port's existing thinking chunk. If
  the port's legacy streaming has no thinking chunk, drop it. Do not add a new
  chunk type in this work.
- oMLX sends each tool call complete in one delta
  (`fixtures/omlx/stream_tool_call.sse`). The existing accumulation handles
  this. Test it with the fixture.

### Keep-alive frames

oMLX opens every chat stream with a keep-alive frame, and sends more during
long prefill. By default it is a real `data:` frame:

```text
data: {"id":"chatcmpl-…","object":"chat.completion.chunk","created":0,"model":"keepalive","choices":[{"index":0,"delta":{"role":"assistant","content":""},"finish_reason":null}]}
```

Every fixture stream starts with one. Its content is empty, so it yields no
content, but its `model` of `keepalive` enters the completion evidence. A
stream that fails during prefill would then report `keepalive` as the
provider model.

The oMLX gateway drops frames whose `model` is `keepalive` before they reach
the shared OpenAI stream parser, in both streaming APIs. Do not change the
OpenAI parser for this. oMLX can also be configured to send an SSE comment
(`: keep-alive`) instead, which the parser already skips.

## 4. Models

| Operation | Request | Result |
| --------- | ------- | ------ |
| available models | `GET /v1/models` | the `data[].id` values, sorted |
| load model | `POST /v1/models/{id}/load` | success when the model is in memory |
| unload model | `POST /v1/models/{id}/unload` | success when the model is out of memory |

- Load blocks until the model is in memory. Use a long timeout. A 31 GB model
  took 4 seconds from oMLX's SSD cache and longer from cold.
- A chat request loads its model automatically. Load is for warming up ahead of
  time.
- Unloading a model that is not loaded is a 400 (`invalid_request_error`).
  Report it as a provider error. Do not hide it.
- oMLX downloads models only through its admin dashboard. There is no pull
  operation.

## 5. Embeddings

`POST /v1/embeddings` with `{model, input: <text>}`. Return
`data[0].embedding`.

- The model is required. oMLX has no standard embedding model, so there is no
  default. A missing model is an argument error before any request.
- One request. No client-side chunking and no tokenizer.
- A chat model returns 400 (`fixtures/omlx/error_not_embedding_model.json`).
  Report it as a provider error.

The success path is not yet captured from a live server, because no embedding
model was installed. Test the request shape and the response mapping with a
fake transport.

## 6. Errors

oMLX errors use the OpenAI shape:
`{"error": {"message": ..., "type": ..., "param": null, "code": null}}`.

| Status | type | Example |
| ------ | ---- | ------- |
| 401 | `authentication_error` | missing or wrong API key |
| 404 | `not_found_error` | unknown model; the message lists the available models |
| 400 | `invalid_request_error` | chat model used for embeddings; unload of a model that is not loaded |

Report each as the port's existing provider error, carrying the status and
the error body. Do not parse the message text.

## Tests

With a fake transport, and the fixtures where one exists:

1. Configuration precedence, default host, `/v1` prefix, and bearer header
   present only with a key.
2. Request body for each config field in section 2, including no
   `max_completion_tokens`, `reasoning_effort` forwarded unchanged, and no
   parameter removed for an unknown model name.
3. `reasoning_content` maps to thinking (`chat_thinking.json`); a response
   without it has null thinking (`chat_thinking_disabled.json`).
4. Tool call parsing (`chat_tool_call.json`) and a tool result round trip
   (`chat_after_tool_result.json`).
5. Structured output request shape, and the `Warning` header recorded in
   metadata.
6. `chat_length.json` maps to finish reason `length` with content unchanged.
7. Events API: `stream_thinking.sse` completes with content only;
   `stream_length.sse` is an incomplete-completion error;
   `stream_tool_call.sse` is an unexpected-tool-calls error. Each fixture's
   evidence carries the real model name, and a stream of only a keep-alive
   frame ends as an incomplete-stream error with no provider model.
8. Legacy streaming: `stream_tool_call.sse` yields one complete tool call.
9. Models list, load, unload, and unload of a model that is not loaded.
10. Embeddings request shape, missing model rejected before a request, and
    the not-an-embedding-model error.

Add one example program that runs a turn against a local server, reading
`OMLX_HOST` and `OMLX_API_KEY`. Do not put a live server in the test suite.
